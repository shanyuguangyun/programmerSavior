01 管理后台不是另一个 CMS

给个人站点做管理端，最容易掉进的坑，是把“管理”理解成“把主站再做一遍”。文章上传、目录管理、编辑器、发布流程全都搬进手机，最后得到一个又重又难用的缩小版后台。

但如果真正回看日常动作，站长在手机上需要的其实很具体：看到一条新评论，判断它是不是垃圾；知道今天有没有人访问；发现某篇文章突然有了阅读量，决定要不要继续写。它更像一个状态面板，而不是内容生产工具。

所以第一版应该主动做减法：文章仍然在电脑上上传，评论审核先在管理端完成，统计只保留最近 7 天和最热门的几篇。把“打开就能做决定”做好，比“什么都能做”重要。

管理后台的价值，不是把所有功能装进口袋，而是把最需要立刻知道的事情放到首屏。

02 先选形态：PWA，还是小程序

这里的“小程序”有两种理解：一种是手机端管理后台，另一种是微信小程序。两者都能做，但第一版的成本差很多。

我的建议是：先用同仓库的移动端 PWA。复用现有 React 项目和 Session 登录，在同一套域名下开 /admin；实时评论用浏览器原生 EventSource；上线只需要部署，不需要审核。

维度 PWA 管理端 微信小程序
开发成本 低，复用现有前端和后端 中高，独立工程与发布流程
登录 复用现有 Session 微信登录 + 管理员账号绑定
实时评论 SSE，浏览器自动重连 WebSocket，需要额外适配
手机通知 Web Push，受系统限制 订阅消息，触达更稳定
适合阶段 MVP 首选 有明确微信场景时再做

如果“小程序”是硬性要求，也不需要推翻后端：接口全部保留，小程序端换一个壳，实时通道从 SSE 换成 wx.connectSocket，登录增加 openid 绑定即可。先做 PWA 并不会让小程序版本白做。

03 首屏只回答三个问题

概览页不做大而全的仪表盘，只放三个数字：

未读评论

新评论有没有被看到。点进去就能处理，处理完数字归零。

今日有效浏览

今天内容有没有被读到。30 分钟内同一访客同一文章只算一次。

今日访客

今天大概有多少不同的人来过。用 UV 判断“热度”比 PV 更可靠。

手机界面大致是这样：顶部是状态，中间是三个数字，下面是最近评论，底部四个 Tab。没有侧栏，也没有需要横向拖动的大表格。

概览 实时连接
未读 8 条评论
今日浏览 126 PV
今日访客 73 UV
最近评论 全部
用 用户e303b868c252 2 分钟前 NEW

这篇关于实时看板的文章很有用，想看看统计部分怎么实现。

管 fengwen 6 分钟前

收到，下一篇会把浏览去重的细节展开。

概览 评论 文章 我的

底部四个 Tab 分别对应：概览、评论、文章、我的。评论页默认进入“未读”，文章页只看浏览趋势，我的页只放通知开关和退出登录。第一版不要做设置中心里的十几项开关。

04 实时评论：SSE 就够了

新评论是典型的单向事件：服务端产生，管理端接收。这里不需要双向通信，也不需要客户端互相广播，所以 SSE 比 WebSocket 更合适。浏览器原生 EventSource 自带断线重连，Spring Boot 2.7 也自带 SseEmitter，对当前的 Java 8 后端没有额外负担。

流程可以很短：评论插入数据库后，发布一个应用事件；事件服务把内容推给所有在线管理员；管理端收到事件后更新未读数，并把新评论插到列表顶部。

AdminEventController.java SSE 
@GetMapping(value = "/api/admin/events",
             produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter events(HttpServletRequest request) {
    Long adminId = AuthSessions.requireAccountId(request);
    SseEmitter emitter = new SseEmitter(30_000L);

    emitter.onCompletion(() -> registry.remove(adminId, emitter));
    emitter.onTimeout(() -> registry.remove(adminId, emitter));
    registry.add(adminId, emitter);

    // 让代理知道这是事件流，不要缓冲
    emitter.send(SseEmitter.event()
        .name("heartbeat")
        .data("ok"));
    return emitter;
}

管理端只接一种主要事件：comment.created。事件里放评论 id、文章 id、文章标题、作者名、内容摘要和时间。不要在事件里塞整篇 HTML，也不要让客户端收到一个还需要二次请求的大对象。

admin-live.ts EventSource 
const source = new EventSource('/api/admin/events')

source.addEventListener('comment.created', (event) => {
  const comment = JSON.parse(event.data)
  unreadCount.value += 1
  comments.prepend(comment)
})

// 断线重连后先补一次 REST 数据，避免漏掉断线期间的事件
source.addEventListener('open', () => {
  refreshUnreadComments()
})

还有几个容易被忽略的工程细节：服务端每 25 秒发一次心跳；Nginx 关掉响应缓冲；页面从后台回到前台时重新拉取未读数量；单实例先用内存注册表，多实例再换 Redis Pub/Sub。

不要用轮询硬扛实时评论。每 2 秒查一次列表，看似简单，实际上会制造无意义的数据库请求，而且手机切回前台时经常漏掉中间状态。SSE + 重连补偿更适合这个场景。

05 浏览量：先定义，再统计

“最近浏览量”听起来是一个数字，实际至少包含 PV、UV 和时间范围三件事。如果不先定义，代码写完以后一定会出现“为什么我刷新了十次，数字只涨了一次”或者“为什么数据这么大”的争论。

指标 定义 用途
有效 PV 30 分钟内同一访客对同一文章只计 1 次 看内容热度
UV 同一天不同访客哈希的数量 看真实到访人数
今日浏览 当天有效 PV 首屏核心数字
热门文章 按最近 7 天有效 PV 排序 决定继续写什么

采集放在阅读页加载时：前端用 sessionStorage 记录当前标签页是否已经上报过；后端再用 IP、User-Agent 和每日盐生成 visitor_hash，按 30 分钟时间桶做唯一约束。这样既能挡住刷新，也不需要依赖第三方统计脚本。

V5__create_ps_post_view.sql MySQL 
CREATE TABLE ps_post_view (
  id BIGINT NOT NULL AUTO_INCREMENT,
  post_id BIGINT NOT NULL,
  visitor_hash CHAR(32) NOT NULL,
  view_bucket BIGINT NOT NULL,
  is_admin TINYINT(1) NOT NULL DEFAULT 0,
  referrer VARCHAR(512) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_view_dedupe (post_id, visitor_hash, view_bucket),
  KEY idx_view_post_created (post_id, created_at)
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_general_ci;

管理员自己的访问默认不计入公开统计。原始浏览事件保留 90 天；数据量变大后，再把每日结果写入 ps_post_stats_daily，管理端优先读聚合表。个人站点不需要第一天就上 ClickHouse，也不需要引入一套复杂的埋点 SDK。

隐私边界要写进设计里：不保存原始 IP，只保存加盐哈希；不采集与统计无关的个人信息；管理端只展示匿名昵称，不展示评论者 IP。

06 数据表与接口

现有评论表已经能支撑评论和回复，管理端只需要补两个状态：评论是否已读，以及浏览事件。文章表继续作为统计的维度表，不重复存标题。

对象 作用 关键字段
ps_comment 评论与无限层级回复 post_id、parent_id、admin_read_at
ps_post_view 浏览事件与去重 visitor_hash、view_bucket、is_admin
ps_post_stats_daily 长期日聚合（P1） stat_date、pv、uv

管理端接口

方法 路径 说明
POST /api/posts/{id}/view 公开浏览上报，静默处理
GET /api/admin/overview 未读数、今日 PV/UV、趋势
GET /api/admin/comments 未读 / 全部评论
POST /api/admin/comments/{id}/read 单条已读
GET /api/admin/events SSE 实时事件流
GET /api/admin/posts 文章浏览列表
GET /api/admin/posts/{id}/stats 单篇趋势

所有管理接口都放在 /api/admin/** 下，统一做管理员 Session 校验。不要靠前端隐藏入口来保护统计和评论数据。

07 三周 MVP 路线

按业余时间推进，建议把工作拆成三段。每一段结束都应该有一个可以验证的结果，而不是等到第三周才第一次跑通。

Week 01

把数据做对

加评论已读字段和浏览事件表；阅读页上报；完成概览、文章列表、单篇统计查询；用 SQL 验证 PV/UV 与去重。

Week 02

把页面做出来

增加 /admin 移动端布局和登录保护；完成概览、评论、文章、我的；接入 SSE；实现未读徽标和断线重连。

Week 03

把体验收干净

375px 适配、空状态、骨架屏、离线提示、PWA manifest、可选的通知开关；补鉴权、限流和基本压测。

第一版明确不做：文章上传、评论删除、敏感词后台、多管理员、复杂来源分析。等功能真的有使用需求，再加。

08 验收清单

功能是否“做完”，不看页面数量，看下面这些行为是否稳定。

  • 新评论提交后 2 秒内出现在管理端，未读数同步 +1。
  • SSE 断开后 5 秒内自动重连，重连后不丢未读评论。
  • 同一访客 30 分钟内刷新同一文章，有效 PV 不重复增加。
  • 管理员访问文章不计入公开浏览量。
  • 手机 375px 宽度无横向滚动，底部 Tab 不遮挡内容。
  • 未登录访问任意 /api/admin/* 返回 401。
  • 概览数据 30 秒内可刷新，加载失败有重试入口。
  • 评论区已有的无限层级回复和 5 条折叠规则不被破坏。

最后，从一条评论开始

不要先做“站长工作台”的大而全版本。先让一条新评论在 2 秒内出现在手机上，再让今天的浏览数在打开页面时可见。只要这两个动作顺畅，管理后台就已经成立了。
